# Exact hash-rank oracle results — 2026-08-12

## Fixture

- Source fixture: `prof_input/input2` (930,723 bytes)
- Production dictionary preprocessing enabled with `dictionary/english.dic`
- Predictor input after preprocessing: 557,621 bytes
- Shared Predictor-stream vocabulary: 204 byte values
- Predictor: production fx2-cmix configuration, 461 models
- Dictionary pretraining enabled
- Samples: 8 positions, warm-up 32,768 bytes, stride 65,536 bytes
- Runner: GitHub Actions `macos-14` (arm64)

For every sampled state, the experiment used process copy-on-write snapshots and
scored every next-byte value allowed by the already-shared vocabulary. Each
candidate followed the real `Predict()` / `Perceive()` path for its first seven
bits; the eighth/final bit was predicted and scored but not committed because no
future probability is needed for a one-byte likelihood.

## Interpretation

This is a positive *search-geometry* result, not yet a compression result.
`log2(rank)` is not by itself a uniquely decodable code length, and the minimum
fingerprint column deliberately excludes any framing or hash-length information.
For example, an Elias-gamma code of the eight observed ranks would use 32 bits
(4.0 bits/sample), which is worse than the 21.121705-bit aggregate fx2
surprisal. Likewise, explicitly self-delimiting each observed fingerprint length
would erase the raw oracle gain.

The experiment therefore rejects the naive form "replace every byte with its
rank/hash". It does, however, show that the production predictor places the real
continuation unusually early in likelihood order often enough to justify the
original block-level idea: use a deterministic candidate search over a longer
segment and amortize fingerprint/framing cost across the whole segment.

## Next experiment

Move from one-byte ranking to a bounded multi-byte search. The next gate should
measure 16-bit/32-bit blocks with branch-and-bound or best-first reconstruction,
recording:

1. actual block surprisal,
2. number/rank of candidates reached before the true block,
3. fixed-length fingerprint success at several bit widths,
4. total uniquely-decodable framing cost,
5. search nodes and wall/CPU cost.

The idea should be killed if block-level framing removes the oracle headroom or
if candidate search grows too quickly to fit Hutter decompression constraints.
